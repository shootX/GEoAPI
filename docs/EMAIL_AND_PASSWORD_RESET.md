# ელფოსტის დადასტურება და პაროლის აღდგენა

production-ის სამივე დროშა ჩართულია. SMTP-ის ჰოსტი, პორტი, TLS, მომხმარებელი, პაროლი და გამგზავნი CarAPI-ის FPM-შია. `mail.socialsave.cc:587`-ის სერტიფიკატი სანდოა. AUTH TLS-ის შემდეგ წარმატებით შემოწმდა. ერთი სატესტო წერილი `sh.chkhvirkia@gmail.com`-ზე გაიგზავნა: SMTP-მ მიიღო და Gmail-მა `250` დააბრუნა. მომხმარებელმა დაადასტურა, რომ ეს ერთი სატესტო წერილი მიიღო. ეს არც მომავალი წერილების მიწოდების გარანტიაა და არც რეგისტრაციის სრული გზის შემოწმება. ტესტები იყენებს `CARAPI_MAIL_TRANSPORT=fake`.

## კონფიგურაცია

აპლიკაცია `.env`-ს არ კითხულობს. ცვლადები პროცესის გარემოდან მოდის. საიდუმლო საერთო PHP-FPM პულში არ წერია; CarAPI-ის runtime ცალკე პულია (`docs/DEPLOYMENT.md`).

| ცვლადი | აზრი |
|---|---|
| `CARAPI_APP_URL` | ბმულის ერთადერთი საბაზისო მისამართი. ლოკალურის გარდა მხოლოდ `https` |
| `CARAPI_MAIL_TRANSPORT` | `smtp` ან ტესტის `fake`. ცარიელი ან არასრული SMTP fake-ზე არ გადადის |
| `CARAPI_MAIL_HOST` | SMTP ჰოსტი |
| `CARAPI_MAIL_PORT` | პორტი, ნაგულისხმევი 587 |
| `CARAPI_MAIL_USERNAME` | SMTP მომხმარებელი |
| `CARAPI_MAIL_PASSWORD` | SMTP პაროლი |
| `CARAPI_MAIL_ENCRYPTION` | `tls` ან `ssl` |
| `CARAPI_MAIL_FROM_ADDRESS` | გამგზავნის მისამართი |
| `CARAPI_MAIL_FROM_NAME` | გამგზავნის სახელი |

SMTP არის `src/Platform/SmtpMailer.php`-ში, PHPMailer-ის გარეშე. TLS სერტიფიკატი მოწმდება, timeout 10 წამია, საუბარი პასუხში არ იბეჭდება. არასრული კონფიგურაცია fake transport-ზე არ გადადის.

2026-09-26: `mail.socialsave.cc` ამავე სერვერის `161.97.78.24`-ია. 587 პორტს ემსახურება Postfix (`submission`). aaPanel-ის ფოსტის მოდული ამ Postfix-ს აყენებს. ადრე STARTTLS თვითხელმოწერილ `vmi3595454.contaboserver.net` სერტიფიკატს იძლეოდა. ახლა Postfix იყენებს უკვე არსებულ Let's Encrypt სერტიფიკატს: გამცემი YR1, CN `*.socialsave.cc`, SAN `*.socialsave.cc` და `socialsave.cc`, მოქმედია 2026-12-22-მდე. სრული ჯაჭვი SMTP სერვისზეა მიბმული. OpenSSL `-verify_return_error` ამ სახელზე წარმატებულია, უცხო სახელზე კი hostname mismatch-ით ეცემა. PHP-ის საცავითაც, `verify_peer` და `verify_peer_name` ჩართული, STARTTLS გადის. სერტიფიკატის შემოწმება არ გამორთულა. AUTH და წერილი არ გაშვებულა.

განახლებას aaPanel-ის cron აკეთებს: `acme_v2.py --renew_v3=1`, ყოველდღე 03:52, როცა ვადამდე 31 დღეზე ნაკლებია. ეს wildcard DNS-01-ითაა აღებული. სატესტო staging სერტიფიკატი SMTP-ზე არ დადგმულა. 04:20-ზე `/etc/postfix/tls/reload-mail-cert.sh` ახალ ჯაჭვს Postfix-ში ტვირთავს და `postfix reload` ასრულებს. aaPanel-ის ფოსტის სერტიფიკატის ხელახალმა დაყენებამ `main.cf` შეიძლება ისევ ძველ გზაზე დააბრუნოს; ჰუკი ამ გზას აღადგენს, თუ წყარო კვლავ `mail.socialsave.cc`-ს მოიცავს. IMAP 993/995 კვლავ Dovecot-ის ძველ სერტიფიკატზეა.

პაროლი იწერება მხოლოდ `/www/server/carapi/mail.env`-ში (`CARAPI_MAIL_PASSWORD`, root, რეჟიმი 600) და პულში გადადის `python3 /www/server/carapi/apply-mail-env.py`-ით. საცდელი გაგზავნა, რომელიც ჯერ არ გაშვებულა: `php bin/send-test-mail.php --to=მისამართი --send`. წარმატების ტექსტია „SMTP სერვერმა მიიღო“.

## ტოკენები

მიგრაცია `migrations/003_email_tokens.sql`. ბაზაში მხოლოდ SHA-256 ჰეშია. დადასტურება 24 საათი, აღდგენა 30 წუთი. ტოკენი ერთჯერადია, მიზანზეა მიბმული და უვარგისია, თუ ელფოსტა `email_snapshot`-ს აღარ ემთხვევა. ერთი მიზნის ტოკენი მეორეს არ ცვლის. პაროლის მოთხოვნა დადასტურების ტოკენს არ აუქმებს. გამოყენება და ანგარიშის ცვლილება ერთ ტრანზაქციაშია.

## მარშრუტები და ლიმიტები

- `POST /email/verification/resend` — სესია და CSRF. წერილი მხოლოდ შენახულ ელფოსტაზე მიდის.
- `GET /email/verify?token=` — ფორმა, ტოკენი არ იხარჯება.
- `POST /email/verify` — CSRF და ტოკენი. შესვლა სავალდებულო არ არის და ავტომატური ავტორიზაცია არ ხდება.
- `GET/POST /forgot-password`
- `GET /reset-password?token=` და `POST /reset-password`

არსებული და არარსებული ელფოსტა ერთსა და იმავე ტექსტს იღებს. ლიმიტი: მისამართზე 1 წუთში და 5 საათში, IP-ზე 20 საათში. ახალი cookie ამას არ ხსნის. ჩვეულებრივი შესვლა ამ ლიმიტით არ იბლოკება. ტოკენის გამოცნობა IP-ზე საათში 10 მცდელობით იზღუდება.

SMTP-ის ჩავარდნა რეგისტრაციას არ შლის და ელფოსტას არ ადასტურებს. პაროლის შეტყობინების ჩავარდნა უკვე შეცვლილ პაროლს უკან არ აბრუნებს.

პაროლის აღდგენა ზრდის `users.auth_version`-ს, ამიტომ ძველი სესიები წყდება. API გასაღებები, პროექტები, suspension და დაუდასტურებელი ელფოსტა უცვლელი რჩება. აღდგენის შემდეგ მომხმარებელი შესვლის გვერდზე რჩება ავტორიზაციის გარეშე.

ტოკენიან გვერდებს აქვს `Cache-Control: no-store` და `Referrer-Policy: no-referrer`. გარე ანალიტიკა არ ერთვის. ბმული მხოლოდ `CARAPI_APP_URL`-იდან იგება.

ტოკენის query string ამ დომენის access log-ში აღარ იწერება. მოქმედი ფორმატია `carapi_safe` (`docs/DEPLOYMENT.md`). ძველი nginx-ის ნიმუში, რომელიც `combined` ლოგს და `$request_uri`-ს ტოვებდა, მოქმედი კონფიგურაცია არ არის.
